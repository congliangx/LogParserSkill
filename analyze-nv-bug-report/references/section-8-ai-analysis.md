# Section 8 AI Deep Analysis

Read this file completely whenever Step 2.7 of the skill applies.

## Evidence to inspect

Before writing, inspect the full generated report, not only the baseline Section 8 bullets:

- Read system/GPU inventory, PCIe, ECC/memory, NVLink, IMEX, and every Message/dmesg subsection.
- Reconstruct event ordering from Xid event groups, primary/derivative counts, BDF/link/subtype data, interleaved NVRM/IMEX context, and boot/log collection times.
- Read targeted context from the original log when the report lacks enough lines to evaluate an important event. Do not read the whole large log without need.
- Treat `N/A`, missing counters, and a truncated input as unavailable evidence, never as proof that a component is healthy.
- When NVBugs lookup succeeded, inspect the search results and the retrieved details for candidates actually used in the analysis.

## Required reasoning

Keep the script-generated Critical/Warning/OK entries visible, then add a concise but substantive synthesis. Audit those entries rather than inheriting their confidence: if an `OK` or health claim is based on missing telemetry, explicitly qualify or correct it in the AI block. Cover:

1. **Overall assessment and impact**: State whether the evidence indicates a healthy snapshot, isolated GPU/application fault, multi-GPU cascade, PCIe/NVLink/Fabric issue, memory/ECC issue, or an unresolved pattern.
2. **Evidence and event sequence**: Identify the first visible failure, subsequent primary events, derivative/containment events, affected BDFs/links/processes, and relevant timing correlations. Do not turn temporal correlation alone into causation.
3. **Scope and localization**: Explain whether evidence is tied to one GPU/link/process, moves across devices, or is synchronized across a node/fabric. Reconcile conflicting signals across sections.
4. **Root-cause hypotheses**: Rank plausible causes, cite evidence for and against each, and assign `high`, `medium`, or `low` confidence. Explicitly distinguish an observed fact from an inference.
5. **Negative evidence and limitations**: State important failures not observed as "not observed in the available log" and identify missing telemetry that limits confidence.
6. **Recommended actions**: Give prioritized, evidence-linked actions for immediate recovery, confirmation/reproduction, data capture, software/firmware validation, and hardware escalation. Define what result would raise or lower each leading hypothesis; avoid generic advice as the only recommendation.

Do not invent Xid semantics, hardware topology, fix versions, bug root causes, or health status. Prefer precise uncertainty over an unsupported conclusion.
Preserve exact BDFs, Xid numbers, mnemonics, raw payloads, timestamps, PIDs, build identifiers, and Bug IDs; translate only explanatory prose when the report language requires it.

## NVBugs synthesis

When the user opted in and lookup succeeded:

- Compare candidate bugs against GPU/platform, Xid number and textual subtype, error payload, event chronology, workload, driver/RM branch, and fix status.
- Use full bug details for a root-cause or fix claim whenever available. If only the title/synopsis is available, say `synopsis-only match` and lower confidence.
- Cite the Bug ID and exact returned title for every candidate used. Explain supporting and contradicting evidence and classify relevance as high, medium, or low.
- Integrate the best-supported bug evidence into the ranked hypotheses and actions, including build/fix verification when the returned bug data supports it. Do not merely repeat the Section 9 table.
- If a successful search returns no materially relevant candidate, state that result and keep the diagnosis log-driven. If MCP is unavailable, obey Step 2.5: omit NVBugs claims and do not imply that lookup succeeded.
