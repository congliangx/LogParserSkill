# Analyze NVIDIA Bug Report Logs

## Overview

Parse log files generated by `nvidia-bug-report.sh`, extract key GPU diagnostic information and output a human-readable report.

> ### 🔴 Ask once, then never silently skip
>
> `analyze.py` produces a **baseline, not a finished report**. The script never
> writes the analysis and never will. Whether the AI pass runs is **the user's
> call, and they must actually make it** — ask at
> [Step 1.5](#step-15-ask-whether-to-run-the-ai-analysis), before the script
> runs, and wait for a real answer. Never infer one from silence.
>
> Whatever they choose, **every report leaves this skill with a
> `### AI Deep Analysis` block**. There are exactly two legal end states:
>
> | User's choice | What goes in the block | Where the depth lives |
> |---|---|---|
> | **run it** | the full analysis | single log → that node's Section 8 ([Step 2.7](#step-27-ai-deep-analysis-in-section-8)) · `--batch` → `cross-node-report.md` §6.1 ([Step 2.6](#step-26-dmesg--messages-analysis)), plus a short pointer block per node |
> | **decline**, or no answer obtainable | the skip marker below, verbatim | nowhere — and the report says so |
>
> ```markdown
> ### AI Deep Analysis
>
> > **AI analysis not run** — declined by the user. This report contains only
> > `analyze.py`'s deterministic Critical/Warning/OK baseline; no AI synthesis was
> > performed, and the entries above have not been audited for unsupported health
> > claims. To add it later, ask for the AI analysis on this report.
> ```
>
> Keep the bolded lead-in **`AI analysis not run`** verbatim — it is what the
> completion check greps for. Replace only the reason after the dash: `declined by
> the user`, or `confirmation could not be obtained (non-interactive run)`.
>
> A silent omission is the one outcome that is never acceptable: a baseline-only
> report reads as finished to anyone who opens it, and the entries in Section 8
> are exactly the ones that need qualifying (`IMEX anomalies` and
> `PCIe link degraded` routinely fire on healthy nodes).
>
> **Definition of done** — before saying the run is finished, or linking /
> pasting / summarizing any report:
> ```bash
> grep -c "### AI Deep Analysis"     <output-dir>/*-analysis-report.md   # each >= 1
> grep -c "### 6.1 Analysis Summary" <output-dir>/cross-node-report.md   # >= 1, batch + analysis run
> grep -l "AI analysis not run"     <output-dir>/*.md                   # empty if they said yes; all reports if not
> ```
> If a report has no block at all, the work is not done — go back to Step 2.7 /
> Step 2.6.
>
> **Left-on-disk counts as delivered.** If a run of `analyze.py` writes a report
> anywhere the user can find it — including its default `report/` directory —
> it is a deliverable, whatever your reason for running the script was. Either
> finish the owed block on it, or delete it and say so.

## Workflow

### Step 1: Prepare Files

If the file is in `.gz` compressed format, decompress first:

```bash
gunzip -k <file>.log.gz
```

### Step 1.5: Ask whether to run the AI analysis

**Ask before invoking `analyze.py`**, not after — the estimate depends only on how many logs were handed over, which is already known, and asking first means the user is not left waiting on a decision they have not been given.

Quote the cost from the measured figures below (2.8M-line GB200 log, driver 580.105.08):

| Scope | `analyze.py` | AI analysis | Total |
|---|---|---|---|
| **1 node** | ~10 s | **1–2 min** | ~1.5–2.5 min |
| **1 rack (18 nodes)** | ~1 min | **7–8 min** | ~8–9 min |

**Quote soft numbers, not the measured ranges** — for the script, “usually under a minute” (one node) / “a minute or two” (a rack); for the AI pass, “a few minutes” / “around ten minutes”. The table is the internal reference. Even the script half varies: it was measured on ~14 MB gzipped, 2.8M-line logs with a warm page cache, and a bigger dump or a cold read takes longer. The AI half was measured on a rack already understood, with one shared fault mode. A node whose evidence has to be chased through the original log runs longer, and a rack whose trays fail in unrelated ways runs longer still. A soft number ages better than a precise one that is wrong on the third try, and it does not invite the user to hold a stopwatch to it.

The AI pass scales with **how many distinct fault modes** the evidence shows, not with node count — the rack figure is only ~4× the single-node figure for 18× the logs, because evidence gathering is shared and the per-node blocks collapse to short pointers (Step 2.7). A rack whose nodes fail in unrelated ways costs more than one clean shared event; a node with several unrelated problems takes considerably longer on its own.

Keep the ask short. Two facts and a question — the baseline is fast and comes straight from the script; the AI pass costs extra minutes and is LLM-generated. Do not sell it with a list of what it finds, and do not claim it is the only way to reach those conclusions. Ask in the user's language.

Single log:

> Baseline report: usually under a minute, straight from the script. AI deep
> analysis: a few more minutes, LLM-generated — quality depends on the model,
> treat it as reference.
> Run the AI analysis?

Batch:

> 18 logs. Baseline reports: usually a minute or two, straight from the script.
> AI deep analysis: around ten minutes, LLM-generated — quality depends on the
> model, treat it as reference.
> Run the AI analysis?

Rules:

- **An explicit answer is required — never assume one.** Silence is not consent and it is not refusal. Ask, then wait. Do not start the AI analysis, and do not write the skip marker, until the user has actually chosen. Offering the analysis as the first / recommended option in a picker is fine; treating an unanswered prompt as a "yes" is not.
- **The only thing that substitutes for an answer is the user having already given one.** If their request already names the AI analysis ("analyze these and write the AI summary", "跑完给我 AI 分析"), that *is* the confirmation — honour it and do not re-ask. A generic "analyze this log" does **not** count: it asks for the report, not for the extra minutes.
- **If no answer can be obtained** — the run is non-interactive (cron, headless, piped) and the user is not reachable — do not guess in either direction. Produce the baseline, write the skip marker, and say plainly in the output that the AI analysis was not run because confirmation could not be obtained and how to request it. A report that silently guessed "yes" costs the user time they did not agree to spend; one that silently guessed "no" ships an unanalysed report.
- **Ask once per invocation.** Do not re-ask mid-run, per node, or on a re-run of the same batch in the same conversation. The answer holds for everything that run produces.
- **If they decline**, still write the skip marker block from the gate above into every report, and say once that the reports are baseline-only and can be analysed later on request. Do not re-argue the case. Then stop — do not analyse anyway.
- **A decline is not sticky.** They can ask for the analysis on the existing `.md` files later; append the block and re-render, no need to re-run `analyze.py`.

### Step 2: Extract and Analyze Key Information

Use the bundled analysis script for automated extraction. The script automatically:
- Extracts system info, lspci, nvidia-smi, dmesg GPU diagnostic data
- Falls back to `/proc/driver/nvidia/gpus/*/information` and dmesg serial numbers when `nvidia-smi --query` fails (e.g. dead GPU causes the entire command to error out)
- Supplements Driver Version, CUDA Version, and OS from `nvidia-smi --query --unit`, `/etc/issue`, and dmesg when not found in the log header
- Extracts Xid errors from ALL available log sections: `Scanning kernel log files` (including `/var/log/kern.log` with previous-boot history), `journalctl -b -0:`, `/var/log/messages`, and standalone `dmesg:` — all sources are mandatory and scanned independently with cross-section deduplication
- Detects Xid errors and invokes `third_party/nvidia_xid_analyzer.py` for deep decoding (mnemonic, severity, HW/SW classification, resolution, etc.)
- Detects derivative Xid entries via two mechanisms: (a) NVRM lines explicitly tagged `caused by previous Xid N`, and (b) **time-inferred**: bare Xid 45 lines emitted within 10s of a primary Xid 145/149 on the same BDF (NVRM driver intermittently drops the textual annotation on later cleanup channels in the same burst). Each xid dict gets `is_derivative` / `caused_by`, with an extra `derivative_inferred=True` flag for the inferred variant so 7.1 can call out the inferred count. Section 7.1 splits Primary vs Derivative counts (and footnotes the inferred subtotal); section 7.2 decodes **every** Xid type (primary and derivative both feed the analyzer so the table reflects all observed mnemonics; downstream `(decoded_xid, mnemonic, resolution)` dedup keeps it compact regardless of how many derivative lines were processed); section 7.3 collapses each `(xid, caused_by)` derivative group to a single representative line per burst with a `# +N more ... suppressed` annotation, so a single Xid 145 + dozens of Xid 45 channel cleanups no longer floods the report
- Parses `/var/log/nvidia-imex.log` for "Node disconnect event detected" ERROR entries only (WARNING and other ERROR types are filtered out), groups them into timeline **event groups**, and intelligently deduplicates repetitive messages
- Correlates IMEX disconnect event groups with Xid bursts by time overlap (+/- 60s) for causal analysis, showing related IMEX **event group numbers** in each Xid Raw Log event group and **interleaving IMEX log lines into the raw log block**
- Generates the deterministic baseline Markdown report and saves it to the log directory. **This output is NOT a finished report** — Section 8 holds only script-generated Critical/Warning/OK bullets until the AI pass in Step 2.7 appends `### AI Deep Analysis`. Do not present, link, summarize or hand off this file before that step is done.

```bash
<SKILL_ROOT>/.venv/bin/python <SKILL_ROOT>/scripts/analyze.py <file>.log
```

Optional arguments:
- `--output-dir DIR`: Specify report output directory (defaults to `report/` subdirectory under the log file location)

Report file is named `<original-filename>-analysis-report.md`, saved in the `report/` directory.

**HTML sidecar output:** alongside every `.md` report (single-file and cross-node), a self-contained `.html` sidecar with the same basename is written to the same directory. The HTML version is the recommended viewer for wide tables (NVLink §5 with 4×18 matrices, the cross-node Xid comparison matrix) — it provides:
- Sticky table header and sticky first column (no horizontal scroll loses context).
- Non-zero numeric cells highlighted; zeros and placeholders muted.
- Auto-generated left sidebar TOC with active-section highlight.
- Click-header table sort, top-bar live row filter, expand/collapse all `<details>`.
- Auto light/dark theme via `prefers-color-scheme`.
- **Copy button** on every raw-log block — per-node: each §7.3 event group, §7.4 Other GPU Related and §7.5 Other Warnings; cross-node: each §4 Xid Unified Timeline event group (whose raw log lives in a table's last column, so only that column is copied — Time / Hostname / BDF / Xid are all restated inside the raw line itself). Each block carries a dimmed `Copy` control at its top-right that brightens on hover; clicking it puts the block's raw log lines on the clipboard (`Copied N lines` confirms) without expanding or collapsing the enclosing `<details>`. Purely a renderer feature — the `.md` carries no button markup, so markdown viewers are unaffected.
- Fully self-contained: CSS+JS embedded, no CDN, opens offline in any browser.

Open with `open <name>.html` (macOS) / `xdg-open <name>.html` (Linux).

The HTML sidecar requires the `markdown` PyPI package (already bundled in the skill's `uv` environment — see the install-paths note above). If `markdown` is missing or HTML rendering fails for any reason, a `[warn]` line is printed to stderr and the `.md` report is still written normally — HTML failure never blocks the markdown output. If a post-edit re-render fails, warn the user and deliver/link only the current Markdown; do not present the stale HTML as current.

**Re-rendering after you edit a `.md` (IMPORTANT):** `analyze.py` renders each `.html` once, from the report as it stands at generation time. Whenever you edit a `.md` afterward — adding the Section 8 AI analysis (Step 2.7), the cross-node `### 6.1 Analysis Summary` (Step 2.6), or a `NVBugs Related Bugs` section (Step 2.5) — its `.html` becomes stale. Re-render it with the bundled renderer (the **same** code `analyze.py` uses), so the HTML always matches the `.md`. **Do NOT hand-roll HTML, regenerate it with any other tool, or write your own HTML — always use this command:**

```bash
<SKILL_ROOT>/.venv/bin/python <SKILL_ROOT>/scripts/nvbug_report/html_renderer.py <report.md> [more.md ...]
```

`--kind` and `--title` are auto-detected from each filename (`cross-node-report.md` → cross-node; anything else → per-node); pass `--kind` / `--title` only to override. You can list several `.md` paths to re-render them in one call. (Re-rendering overwrites the stale sidecar in place; the one-time duplicate render is negligible.)

**Platform support:** Linux and macOS. Batch mode runs each log in its own process (Linux uses `fork`, macOS uses `spawn` — same throughput, slightly slower per-worker cold start on macOS).

#### Batch Analysis Mode

Analyze multiple nv-bug-report files and generate a cross-node Xid comparison report:

```bash
# Batch analyze multiple files
<SKILL_ROOT>/.venv/bin/python <SKILL_ROOT>/scripts/analyze.py --batch file1.log.gz file2.log.gz file3.log.gz --output-dir DIR

# Batch analyze all nv-bug-reports in a directory
<SKILL_ROOT>/.venv/bin/python <SKILL_ROOT>/scripts/analyze.py --batch /path/to/logs/*nv-bug-report*.log.gz --output-dir DIR
```

Batch mode will:
1. Analyze each file individually, generating its own analysis report
2. Generate a `cross-node-report.md` comparison report containing:
   - File overview (hostname, system SN, chassis SN, slot#, tray#, boot time, message start time, collect date)
   - IMEX Node Disconnect Timeline (all nodes' "Node disconnect event detected" ERROR entries merged and sorted by time, grouped by burst, gap > 1 min = new event group)
   - Xid comparison matrix (node × Xid number) + companion subsection 3.1 NVLink Sub-type Breakdown (per host × GPU × Xid 144-150 × Category × Severity, long format; collapsed by default; entire subsection omitted when no Xid 144-150 anywhere in the batch)
   - Xid unified timeline (all files' Xid merged and sorted by time, grouped by burst, gap > 1 min = new event group; each event group annotated with related IMEX disconnect event groups within +/- 1 min, and given a **Copy** button in the HTML sidecar that yields its raw log lines)
   - Xid decode summary (merged and deduplicated)
   - Cross-node comparison summary (common/unique Xid types analysis; agent appends dmesg/messages cross-node Analysis Summary as subsection 6.1 per Step 2.6)

If the script is unavailable or fails, follow the manual analysis flow below.

### Step 2.5: NVBugs Xid Association Search (Optional, disabled by default)

**By default, skip this step entirely. Do NOT call any NVBugs MCP tool, do NOT append any NVBugs section to the report, and do NOT add any fallback note unless the user explicitly asks for NVBugs lookup.**

Run this step only when the user's request explicitly opts in to NVBugs lookup (natural-language signals: "search nvbugs", "look up related NVBugs", "include NVBugs related bugs", "查 nvbug", "搜索 nvbugs", "查相关 bug", or any equivalent phrasing). When the user does not explicitly opt in, silently skip this step and continue with the normal report workflow.

**When the user explicitly requests NVBugs lookup, still skip this step entirely (do NOT append any NVBugs section to the report; do NOT add any fallback note) if ANY of the following holds:**

1. **MCP unavailable** — on the first `nvbugs_search` call attempt:
   - server `user-MaaS NVBugs` is not registered, OR
   - the call returns a connection / timeout / authentication error, OR
   - the call returns an unrecoverable error (not a "no results" empty response — empty results are still a successful call and are simply rendered as an empty subsection)

   When this happens, abort the entire NVBugs subsection (do not retry per Xid type), and tell the user once in chat ("NVBugs MCP unavailable, skipping NVBugs search.").

2. **No Xid evidence** — both Section 7.1 and the Xid raw-log section contain zero Xid entries. A missing/failed decoder or an empty Section 7.2 is not evidence that no Xids exist. Silently skip only when the extracted report itself contains none; do not mention in chat.

Otherwise, after report generation use MaaS NVBugs MCP to search related bugs and append to the report.

**Procedure:**

1. Extract the deduplicated Xid type list from Section 7.2 when available; otherwise fall back to Section 7.1 plus raw Xid text and mark an unavailable mnemonic as unknown
2. Get the GPU model (e.g. GB200) from each single-node report's Section 2; in batch mode build distinct `(GPU model, Xid type)` pairs instead of assuming one model for every node
3. For each unique Xid type, call the `nvbugs_search` MCP tool for semantic search:
   - server: `user-MaaS NVBugs`
   - toolName: `nvbugs_search`
   - arguments: `{ "query": "GPU Xid {number} {mnemonic} on {gpu_model}", "search_type": "semantic", "max_results": 5 }`
4. Skip Xid 45 (preemptive cleanup, typically triggered by other Xid, not an independent issue)
5. Extract bug ID, title, severity, disposition from search results
6. For the 1-3 candidates most consistent with the observed GPU model, Xid subtype, event sequence, workload, and driver/RM context, retrieve the available bug details (description, analysis/root cause, affected/fixed builds, resolution, and relevant comments) with a read-only NVBugs detail tool. If no detail tool is available, retain the synopsis-only evidence and label it as such in Step 2.7; never promote a title-only match to a confirmed root cause.
7. Append results to the end of the report file as the next sequential section (e.g. "9. NVBugs Related Bugs" for single-node reports, "7. NVBugs Related Bugs" for comparison reports — use the next number after the last existing section)

**Example search queries:**
- `"GPU Xid 145 NVLINK_RLW_ERROR on GB200"`
- `"GPU Xid 79 GPU fallen off the bus"`
- `"GPU Xid 119 GSP_RPC_TIMEOUT"`

**Report append format:**

The entire NVBugs section MUST start with an LLM-generated disclaimer note and wrap ALL Xid subsection tables in a single collapsible `<details>` block:

```markdown
## N. NVBugs Related Bugs
(N = next section number after last existing section in the report)

> **Note**: This section is generated by the LLM agent based on NVBugs semantic search results. For reference only — verify bug relevance before action.

<details>
<summary>Click to expand NVBugs search results</summary>

### Xid 145 (NVLINK_RLW_ERROR)

| Bug ID | Title | Severity | Disposition |
|--------|-------|----------|-------------|
| 12345678 | NVLink RLW error on GB200 ... | P2 | Open |
| 12345679 | ... | P1 | Fixed |

### Xid 137 (NVLINK_PRIV_ERR)

| Bug ID | Title | Severity | Disposition |
|--------|-------|----------|-------------|
| ... | ... | ... | ... |

</details>
```

Markdown formatting requirements for the collapsible block:
- No blank line between `<details>` and `<summary>`
- Keep one blank line after `</summary>` before markdown content
- Keep blank lines before and after each markdown table

**Batch mode:** Append once to `cross-node-report.md`, grouping results by GPU model and Xid type (for example, `### GB200 — Xid 145 (...)`). Retain the per-node mapping for Step 2.7; do not apply a candidate from one model to another unless its returned evidence explicitly supports both.

After appending the NVBugs section, retain the search and detail evidence for Step 2.7. Defer HTML rendering until all agent edits are complete, then re-render every modified `.md` once with the bundled renderer.

### Step 2.6: dmesg / messages Analysis

`analyze.py` automatically scans both the `dmesg:` section and syslog/messages sections (`journalctl`, `/var/log/messages`), deduplicates across sections, and embeds non-GPU warnings as **Section 7.5 Other Warnings** (after 7.4 Other GPU Related). GPU/NVIDIA/PCIe related lines are excluded from 7.5 — they are already covered by 7.3 (Xid Raw Logs with interleaved NVRM context) and 7.4 (Other GPU Related).

The embedded highlights have two categories:
- **System Errors** — kernel panic, oops, OOM, MCE, hardware errors, etc.
- **Other Warnings** — timeouts, temperature, network, storage warnings, etc.

**Agent Procedure (Comparison Report Only):**

**Trigger: any `--batch` run that leaves a `cross-node-report.md` behind, unless the user declined at [Step 1.5](#step-15-ask-whether-to-run-the-ai-analysis).** Like Step 2.7, this is not "when the user asks for a cross-node summary" — the moment that file exists on disk, section 6.1 is owed on it. On a decline, write the skip marker into the cross-node report too: it is the file that carries the findings no single node can show, so its absence is the most expensive one to leave unmarked. `analyze.py` writes Section 6's common/unique Xid tables and the IMEX-Xid correlation list, and stops there; `### 6.1 Analysis Summary` is agent-written or absent.

For single-node reports, section 7.5 is auto-generated — no agent action needed.

For comparison reports (batch mode), append the cross-node dmesg/messages analysis **into Section 6 (Cross-Node Comparison Summary)** as subsections, directly after the auto-generated Xid comparison content (common/unique Xid, IMEX-Xid correlation). Do NOT create a separate top-level section.

1. Read each complete single-node report; use Sections 1-7.4/7.6 for GPU/fabric evidence and Section 7.5 for non-GPU system evidence
2. Append a single `### 6.1 Analysis Summary` subsection under section 6. It MUST start with an LLM-generated disclaimer note and wrap its content in a collapsible `<details>` block. Group findings by theme (omit a theme if no relevant data) — do NOT split into separate "Issue Summary" and "System-Level Analysis" subsections:

```markdown
### 6.1 Analysis Summary

> **Note**: This subsection is generated by the LLM agent by reading each node's report, including section 7.5. For reference only.

<details>
<summary>Click to expand Analysis Summary</summary>

Group findings by theme. Recommended themes (omit a theme if no relevant data):

- **Xid Overview**: how many nodes have Xid errors, dominant Xid types, nodes with no Xid
- **Most Affected Node(s)**: which node has highest Xid count or unique critical Xid types, with escalation chain
- **Multi-Node / Fabric-Level Failure**: simultaneous Xid bursts across nodes, same Chassis SN, fabric-level inference
- **IMEX <-> Xid Correlation**: which IMEX events overlap which Xid events; IMEX import failures across nodes
- **Causal Chain**: dominant Xid causal sequence (e.g. Xid 145 -> Xid 45) and any escalated chain on specific nodes
- **System-Level Health**: kernel panic / oops / OOM / MCE / hardware errors (state "none" if absent); non-GPU misc (disk reset, fuse taint, overlayfs, etc.) with brief impact note
- **Operational Traces**: any manual troubleshooting evidence (e.g. nvidia-smi -r, kill -9 GPU procs, container toolkit reinstall) found in section 7.5

</details>
```

Markdown formatting requirements for the collapsible blocks:
- No blank line between `<details>` and `<summary>`
- Keep one blank line after `</summary>` before markdown content
- Keep one blank line before `</details>`

**In batch mode Section 6.1 IS the deep analysis** — it carries the ranked root-cause hypotheses with confidence levels, the negative evidence and limitations, and the prioritized recommended actions that a single-node report would put in Section 8. Read [Section 8 AI Deep Analysis](references/section-8-ai-analysis.md) and apply its required reasoning areas here, at rack scope. Two additions on top of the per-node contract:

- **Attribute every node-specific finding to its node by hostname**, so it survives being read at rack level: which tray escalated, which links are FEC outliers, which nodes recorded nothing. The short per-node blocks (Step 2.7) point back here, so anything omitted here is omitted everywhere.
- **Separate fabric-scope findings from node-local ones explicitly.** A node-local fault that merely happened on the same day as a shared event must not be folded into it.

**Notes:**
- If more context is needed (e.g. 10 lines around an error), use the Read tool to directly read the original log file
- If a node's 7.5 section is empty or missing, omit only its 7.5-derived themes; do not discard its GPU/Xid evidence
- After appending `### 6.1 Analysis Summary`, defer HTML rendering until all agent edits are complete, then re-render every modified `.md` once with the bundled renderer.
- **Verify before reporting completion.** A batch run owes N Section 8 blocks plus this one; check both before telling the user the analysis is done:

  ```bash
  grep -c "### AI Deep Analysis"     <output-dir>/*-analysis-report.md
  grep -c "### 6.1 Analysis Summary" <output-dir>/cross-node-report.md
  ```

  Any `0` means that report is unfinished. Re-running `analyze.py` overwrites both blocks, so re-append and re-render after every regeneration, then check again.

### Step 2.7: AI Deep Analysis in Section 8

**Trigger: any run of `analyze.py` that leaves a report behind, unless the user declined at [Step 1.5](#step-15-ask-whether-to-run-the-ai-analysis).** Not "when the user asks for deep analysis" — the moment a `.md` report exists on disk this step is owed on it, and a decline discharges the *analysis*, never the *block*: write the skip marker instead, so no report ships looking finished when it is not.

Treat `analyze.py`'s Critical/Warning/OK entries as the deterministic baseline, not the finished Section 8. **Every** per-node report gets an `### AI Deep Analysis` block; how deep it goes depends on the mode.

#### Single log — full depth

1. Complete the optional NVBugs lookup first when the user requested it.
2. Read [Section 8 AI Deep Analysis](references/section-8-ai-analysis.md) completely, then append its required `### AI Deep Analysis` block inside Section 8, after all baseline entries and before the next top-level section. Keep every baseline entry visible, but explicitly qualify or correct any unsupported health claim in the AI block. Use the user's requested language, or match the existing report language when none was specified.

#### `--batch` — short block per node

The rack-level reasoning belongs in `cross-node-report.md` §6.1 (Step 2.6); writing it out again per node produces near-identical prose that hides the few things that are actually node-specific. Each per-node block is therefore two parts, and **both are required**:

1. **Pointer** — one or two sentences stating that this node's events are accounted for by the cross-node analysis, naming the event group(s) it belongs to and the file/section to read (`cross-node-report.md` §6.1). Give the node's own counts so the reader can confirm the match without leaving the page.
2. **Node-specific findings** — everything true of *this* node and not of the batch. Write "no node-specific findings; this node is a witness to the shared event only" when that is the case; never leave the part out. A finding qualifies when it is something an engineer holding only this tray would have to act on or explain:
   - any **Fatal**-severity Xid, or an Xid type absent from the rest of the batch
   - an **event group unique to this node** (not shared with any peer)
   - **no Xid at all** while peers recorded some — state whether the capture window actually covers the peers' events, since a post-event reboot makes the zero weak evidence
   - a **FEC outlier**: worst link well clear of that node's own second-worst link, with meaningful bin-5+ traffic (the ratio is what separates a bad link from a broadly noisy GPU)
   - non-zero **ECC or row remapping**, a **fallen-off-the-bus** event, a **System Errors** block in §7.5, or a GPU reset / driver reload in the log

Keep the same `<details>` structure and disclaimer note as the full block. Do not restate the rack-wide causal chain, hypotheses or limitations — §6.1 owns those, and duplicating them is what this split exists to avoid.

#### Both modes

1. If NVBugs lookup succeeded, synthesize the relevant search and detail evidence into the diagnosis, confidence, and recommended actions — in single-log mode inside Section 8, in batch mode inside §6.1; a result table alone is insufficient. If lookup was skipped or unavailable, follow Step 2.5 and base the analysis only on available log evidence.
2. Re-render every modified Markdown report with `html_renderer.py`. Do not deliver a report whose Section 8 lacks this AI block. If rendering fails, deliver the Markdown with a warning and do not present the stale HTML as current.
3. **Verify before reporting completion.** Run the checks below over every report this invocation produced; a `0` on any line means that report is unfinished:

   ```bash
   grep -c "### AI Deep Analysis"     <output-dir>/*-analysis-report.md
   grep -c "### 6.1 Analysis Summary" <output-dir>/cross-node-report.md   # batch only
   ```

   Only after every count is `>= 1` may you tell the user the analysis is complete. If you regenerate a `.md` for any reason (re-running `analyze.py`, changing the renderer, fixing a section), the block is overwritten — re-append it and re-render, then run the check again.

### Step 3: Manual Analysis Guide

#### 3.1 Basic Information

Extract from file header (first 70 lines):
- Date, hostname, kernel version, OS distribution
- NVIDIA driver version, CUDA version
- GPU count and model summary

#### 3.2 lspci Analysis

Three lspci sections exist in the file:

| Section | Focus |
|---------|-------|
| `/sbin/lspci -nntv` | PCI topology tree, quick GPU count and placement check |
| `/sbin/lspci -nn` | Identify all NVIDIA 3D controllers (`[0302]`), note BDF addresses |
| `/sbin/lspci -nnDvvvxxxx` | **Key**: check the following fields for each GPU device |

For each GPU (search `3D controller.*NVIDIA`), check:

1. **PCIe Link Status**: compare `LnkCap` and `LnkSta`
   - Normal: `LnkSta: Speed XXG/Ts (ok), Width xN (ok)`
   - Abnormal: `(downgraded)` indicates link degradation
   - Check whether Speed and Width reach LnkCap expected values

2. **Device Status** (`DevSta`):
   - `CorrErr+` = correctable error
   - `NonFatalErr+` = non-fatal error
   - `FatalErr+` = **fatal error (critical)**
   - `UnsupReq+` = unsupported request

3. **AER Errors**:
   - `UESta:` uncorrectable error status (items with `+` are abnormal)
   - `CESta:` correctable error status
   - Watch for: `DLP+`, `SDES+`, `FCP+`, `CmpltTO+`, `MalfTLP+`

4. **PCIe BAR Region**: check BAR memory mappings
   - Region numbers vary by GPU model (e.g. Region 0/2/4 for GB200, Region 0/1/3 for H20) — they are auto-detected from lspci data
   - Abnormal: Region marked `[disabled]` or `[virtual]` (no physical address assigned)
   - Abnormal: Region sizes differ between same-model GPUs

#### 3.3 nvidia-smi Analysis

Search `/usr/bin/nvidia-smi --query`, for each GPU (starting with `GPU 0000xxxx:xx:xx.x`) extract:

| Field | Search Keyword | Anomaly Criteria |
|-------|---------------|-----------------|
| Name/SN/UUID | `Product Name`, `Serial Number`, `GPU UUID` | Identification |
| PCIe Link | `Link Width Current` | Mismatch with Max is abnormal |
| ECC Errors | `ECC Errors` section | Uncorrectable > 0 is abnormal |
| Retired Pages | `Retired Pages` | Any retired pages need attention |
| Remapped Rows | `Remapped Rows` | Uncorrectable > 0 or Pending=Yes is abnormal |
| Temperature | `GPU Current Temp` | Large variance (>10°C) between GPUs needs attention |
| Power | `Power Draw` | Large variance between GPUs needs attention |
| Clock Events | `HW Slowdown`, `HW Thermal Slowdown` | Active is abnormal |
| NVLink | Search `nvidia-smi nvlink --errorcounters` | error count > 0 needs attention |

#### 3.4 dmesg / messages Analysis

Search ALL of the following sections for Xid and NVRM errors:

1. **`Scanning kernel log files for NVIDIA kernel messages:`** — MUST be scanned; contains `/var/log/kern.log` which may hold Xid from **previous boots** not present in current-boot journalctl or dmesg
2. **`journalctl -b -0:`** — current boot syslog
3. **`/var/log/messages`** — alternative syslog (present on some systems)
4. **`dmesg:`** — current boot kernel ring buffer

> **Important**: All four sources MUST be scanned independently. Do NOT skip any section even if another section is found — kern.log often contains historical Xid from prior boots that journalctl -b -0 does not include.

Within these sections, search for:

1. **Xid Errors**: search `NVRM.*Xid` or `Xid.*nvidia`
   - Record each Xid's timestamp, GPU BDF, Xid number
   - Common critical Xids: 13(GR), 31(GPU memory page fault), 43(GPU stopped), 45(preemptive cleanup), 48(DBE), 61/62/63(internal firmware), 64(ECC page retirement/row remap), 69(graphics context), 74(NVLink), 79(GPU fallen off bus), 92/94/95(high single/double-bit ECC)
   
2. **GPU Fallen Off**: search `fell off the bus`, `GPU has fallen off`
3. **NVRM Errors**: search `NVRM:` lines excluding `loading` and `Persistence`
4. **PCIe AER**: search `AER`, `PCIe Bus Error`

- If there are multiple GPUs, **comparing each GPU's status individually** is key to finding the anomalous GPU
